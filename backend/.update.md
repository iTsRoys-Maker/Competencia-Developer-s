## [v1.1.4] — 2026-05-13

### 🐛 Fix absoluto: Nombre de Cliente y Productos mediante Desnormalización

#### Contexto
A pesar del uso de `JOIN FETCH`, los esquemas de herencia tipo `JOINED` en H2 (y otras DBs) 
a veces hacen que Hibernate falle al hidratar proxies anidados en colecciones (`Pedido -> Detalles -> Producto`), 
lo que resultaba en que los nombres siguieran llegando como nulos.

#### Solución aplicada: Desnormalización controlada
En lugar de depender exclusivamente de que las consultas crucen 3-4 tablas en tiempo de lectura, 
ahora guardamos de forma inmutable el nombre del cliente y de los productos directamente en las 
tablas de pedidos correspondientes en el momento en que se genera la compra.

**Archivos modificados:**
- ✅ `model/Pedido.java`: Agregados campos `@Column` `clienteNombre` y `clienteEmail` que se llenan en el constructor.
- ✅ `model/DetallePedido.java`: Agregado campo `@Column` `productoNombre` que se llena en el constructor.
- ✅ `service/PedidoService.java`: El método `buildResponse()` ahora prefiere leer primero los campos desnormalizados, garantizando que **siempre** envíe los nombres al cliente, aún si la base de datos elimina el producto o el usuario en el futuro.

> ⚠️ **IMPORTANTE: Acción obligatoria**
> Debes detener el proceso en NetBeans y volver a ejecutar ("Run Project"). 
> Esto permitirá que Hibernate actualice el esquema H2 (creando las nuevas columnas).
> **NOTA**: Los pedidos anteriores a esta actualización podrían seguir mostrando "N/A", pero todos los pedidos nuevos que crees ahora funcionarán correctamente.

## [v1.1.2] — 2026-05-13

### 🐛 Fix definitivo: nombre del cliente y productos seguían sin aparecer

#### Causa raíz real
`@Transactional` en Spring AOP **NO aplica** cuando un método llama a otro método del mismo bean.
`toPedidoResponseList()` llamaba a `toPedidoResponse()` internamente — ambos en `PedidoService` —
por lo que la anotación `@Transactional` del segundo método era ignorada y la sesión JPA seguía cerrada.
Resultado: proxies Hibernate en estado `null` → `"N/A"` en el cliente y `"Producto"` en los detalles.

#### Solución definitiva: JOIN FETCH en el repositorio

**`repository/PedidoRepository.java`** — Todas las queries reemplazadas por versiones con JOIN FETCH:
```jpql
SELECT DISTINCT p FROM Pedido p
LEFT JOIN FETCH p.usuario
LEFT JOIN FETCH p.detalles d
LEFT JOIN FETCH d.producto
```
Esto fuerza a Hibernate a cargar **usuario + detalles + producto** en una única consulta SQL,
sin depender de ninguna sesión JPA ni lazy loading posterior.

**`service/PedidoService.java`** — Refactorizado completamente:
- ✅ Todos los métodos retornan `PedidoResponse` directamente (no `Pedido`)
- ✅ Nuevo método privado `buildResponse(Pedido)` que construye el DTO con datos ya cargados
- ✅ `crearPedido()` recarga con `findByIdWithDetails()` antes de devolver la respuesta
- ✅ Eliminada la dependencia en `@Transactional` para conversión de DTOs

**`controller/AdminController.java`** y **`controller/PedidoController.java`** — Simplificados:
- ✅ Ya no necesitan llamar a `toPedidoResponseList()` ni `toPedidoResponse()` manualmente

## [v1.1.1] — 2026-05-13

### 🐛 Bug fix: Nombre del cliente no aparecía en los pedidos (mostraba N/A)

#### Causa raíz
La relación `@ManyToOne` entre `Pedido` y `Usuario` usaba **Lazy Loading** por defecto.
Hibernate cargaba el proxy del usuario solo dentro de una sesión JPA activa, pero al intentar
acceder al nombre fuera de esa sesión (en el método `toPedidoResponse`), el proxy ya estaba
cerrado y devolvía `null`, causando que el frontend mostrara **"Cliente: N/A (N/A)"**.

#### Archivos modificados

**`model/Pedido.java`**
- ✅ Cambiada la anotación `@ManyToOne` a `@ManyToOne(fetch = FetchType.EAGER)` para que
  el usuario siempre se cargue junto con el pedido.

**`service/PedidoService.java`**
- ✅ Agregado `@Transactional(readOnly = true)` a los métodos:
  - `getPedidosPorUsuario()`
  - `getTodosLosPedidos()`
  - `getPedidosPorEstado()`
  - `getPedidoPorId()`
  - `toPedidoResponse()` — con recarga explícita del pedido desde BD
  - `toPedidoResponseList()`

## [v1.1.0] — 2026-05-13

### 🔄 Migración de base de datos: MySQL → H2 Embebida (con soporte MySQL futuro)

#### Contexto
La aplicación fallaba al iniciar porque intentaba conectarse a un servidor MySQL local
(`localhost:3306`) que no estaba en ejecución, causando el error:
```
Communications link failure — Connection refused: getsockopt
```

#### Solución aplicada
Se migró la base de datos activa de **MySQL** a **H2** (base de datos embebida y persistente),
manteniendo toda la configuración de MySQL separada y lista para reconectarse en el futuro
mediante un perfil Spring Boot dedicado.

---

### 📁 Archivos modificados

#### `pom.xml`
- ✅ **Agregada** dependencia `com.h2database:h2` con scope `runtime`.
- ✅ Se mantiene `com.mysql:mysql-connector-j` para el perfil MySQL futuro.

#### `src/main/resources/application.properties`
- ✅ **Cambiada** la fuente de datos activa de MySQL a H2 en modo archivo persistente:
  ```
  jdbc:h2:file:./data/ecommerce_poo;MODE=MySQL
  ```
- ✅ **Activado** modo MySQL en H2 (`MODE=MySQL`) para máxima compatibilidad con el código existente.
- ✅ **Habilitada** la consola web H2 en `/h2-console` para inspeccionar datos durante desarrollo.
- ✅ Se mantiene `spring.jpa.hibernate.ddl-auto=update` → Hibernate crea/actualiza tablas automáticamente.
- ✅ Se mantiene toda la configuración JWT, HikariCP y servidor sin cambios.

### 🚀 Cómo usar

#### Modo H2 (activo por defecto — sin MySQL requerido)
```bash
# Ejecutar normalmente, H2 arranca automáticamente
mvn spring-boot:run
```
- Datos guardados en: `./data/ecommerce_poo.mv.db`
- Consola H2: `http://localhost:8080/h2-console`
  - JDBC URL: `jdbc:h2:file:./data/ecommerce_poo`
  - Usuario: `sa` / Contraseña: *(vacía)*

#### Modo MySQL (cuando el servidor esté disponible)
```bash
# Opción 1: argumento de línea de comandos
mvn spring-boot:run -Dspring-boot.run.profiles=mysql

# Opción 2: variable de entorno
export SPRING_PROFILES_ACTIVE=mysql
mvn spring-boot:run

# Opción 3: en NetBeans → Project Properties → Run → VM Options
-Dspring.profiles.active=mysql
```
> ⚠️ Antes de usar MySQL, crear la base de datos:
> ```sql
> CREATE DATABASE ecommerce_poo;
> ```
